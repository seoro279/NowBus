## 1-A. 실사용 1차 피드백 반영 (2026-09-19, v2~v3)

사용자가 보고한 불만 두 개를 받아 고쳤다. 둘 다 "짐작으로 먼저 만들지 말 것"을
지킨 결과 - 일주일 써 보고 나온 실제 불편이다.

### (1) 장소를 좌표 없이 추가 [F-19]

`GET /api/geocode?q=&lat=&lon=` · `nowbus search` · 앱의 '장소 추가' 화면(세 번째
화면). `nowbus place add 집` 처럼 좌표를 생략하면 검색 결과에서 번호로 고른다.

공급원 두 개를 **번갈아** 담는다 (`providers/geocode.py`).

- `StopGeocoder` — DB 의 정류장 12,897곳 이름. 키도 네트워크도 필요 없다. **항상 켜짐.**
- `KakaoGeocoder` — `NOWBUS_KAKAO_REST_KEY` 가 있을 때만. 건물·상호·주소.

**카카오는 사용자 로컬에서 실물 확인 완료다** (2026-09-19, keyword·address 양쪽).
documents 키가 파서와 정확히 일치했다. `tests/test_geocode.py` 의 두 샘플이
그 키 구성을 그대로 반영하므로, 스펙이 바뀌면 그 테스트가 먼저 깨진다.

| 엔드포인트 | 실물 documents 키 |
|---|---|
| `keyword.json` | address_name, category_group_code, category_group_name, category_name, distance, id, phone, place_name, place_url, road_address_name, x, y |
| `address.json` | address, address_name, address_type, road_address, x, y |

`dapi.kakao.com` 은 개발 컨테이너에서 막혀 있다(버스 API 와 같은 정책).
다시 확인할 일이 생기면 로컬에서 한다:

```zsh
python scripts/smoke_geocode.py "강남역 스타벅스"
```

사용자가 로컬에서 돌려 받은 실물 오류 두 개 (둘 다 파싱 문제가 아니었다):

| 응답 | 원인 | 조치 |
|---|---|---|
| `UnicodeEncodeError` (스택 트레이스) | 안내문의 자리표시자 '발급받은키' 를 `.env` 에 그대로 넣었다. HTTP 헤더는 ASCII 만 담는다 | 키를 헤더에 넣기 전에 검사하도록 고쳤다 (`usable_kakao_key()`) |
| `403 NotAuthorizedError: App(Nowbus) disabled OPEN_MAP_AND_LOCAL service.` | 키는 정상. 카카오 앱에서 **지도/로컬 서비스가 꺼져 있었다** | 콘솔 > 제품 설정 > '카카오맵' 활성화. 스크립트가 이 메시지를 해석해 안내한다 |

**키를 다시 발급하게 만들지 말 것.** 두 번 다 키 문제가 아니었다.

실패하면 **응답 본문을 그대로 찍는다.** 카카오가 거부 이유를 본문에 적어 주므로
'REST 키가 아니다' 와 '이 앱에 로컬 API 권한이 없다' 를 여기서 구분한다. 처음
붙였을 때 401 이 났고, 그때 본문을 안 찍어서 원인을 못 봤다 - 그래서 고쳤다.
키는 헤더에 넣기 전에 검사한다(ASCII·공백). 안내문의 자리표시자를 `.env` 에
그대로 넣어 httpx 가 UnicodeEncodeError 로 죽은 사례가 있었다.

원본 응답을 `tests/fixtures/{keyword,address}_kakao.json` 에 저장한다. 필드명이
다르면 **픽스처를 보고 `_parse_kakao()` 를 고칠 것. 추측으로 고치지 말 것** (§3 과
같은 이유). `tests/test_geocode.py` 의 샘플은 손으로 만든 것이라 '문서대로 오면
이렇게 읽는다'까지만 증명한다.

정류장 좌표를 장소로 저장하면 도보 시간이 0 에 가깝게 잡혀 판정이 무의미해진다.
CLI 와 앱 모두 `source == "stop"` 일 때 경고한다. 지우지 말 것.

### (2) 1~2분 뒤 도착 버스 — RUN 등급 [F-20]

불만 원문: *"충분히 뛰어서 정류장까지 도착할 수 있는데 이런게 안나오면 결국
네이버를 다시 찾아볼 수 밖에 없게 돼."*

원인은 `pick_boardable()` 이 걷기 기준 MISS 를 건너뛰고 다음 차를 고르는 것이었다.
버그가 아니라 설계대로였고, 등급이 하나 없었던 것이다.

- `Catch.RUN` 추가 — TIGHT 와 MISS 사이. 걸어선 늦지만(margin<0) 뛰면 닿는다.
- `pick_sprint()` 를 **따로** 만들었다. `pick_boardable()` 에 섞지 않은 이유:
  1분 뒤 차(뛰면 잡음)가 9분 뒤 차(여유 있음)를 가려버린다. 둘은 서로를 대체하지
  못하므로 양쪽 다 살아 있어야 한다.
- `plan_now()` 가 `PlanSet(best, sprint)` 를 돌려준다. **랭킹(§6.4.1)은 손대지
  않았다** - 점수로 합치면 벌점 없이는 뛰는 후보가 화면을 독점하고, 벌점을 얹으면
  상위 5개에서 밀려 아예 안 보인다(실사용에서 후자였다).
- 필터 하나: 걸어서 잡는 최선보다 총 소요시간이 짧지 않으면 뛰는 후보를 버린다.
  뛰어서 얻는 게 없으면 뛸 이유가 없다. `best` 가 비었을 때는 전부 남긴다.
- 상한: `MAX_RUN_MIN=3.0` 분. `RUN_SPEED=140 m/min`. **둘 다 추정값이다**
  (D-11·D-12). 신호등 대기는 모델에 없다.

응답의 `sprint` 와 `items` 는 **같은 정류장·노선이 겹칠 수 있다.** 버그가 아니다 -
'뛰면 2분 뒤 차 / 안 뛰면 12분 뒤 차' 가 둘 다 사실이다.

곁가지로 하나 고쳤다: `PlanItem.is_estimated` 가 스키마에는 있는데 `_to_item()` 이
채우지 않아 '배차간격 추정' 태그가 한 번도 뜨지 않았다. 이제 `Plan` 이 들고 간다.

### (3) 즐겨찾기 삭제

검색으로 추가가 쉬워지니 곧바로 요청이 왔다 (예상대로였다). 설계서 F-08 에
'등록/조회/삭제 · 필수' 로 이미 적혀 있었는데 삭제만 안 만들어져 있었다.

`DELETE /api/places?name=` · `nowbus place rm` · 홈의 '편집' 모드.

두 가지가 설계 판단이다.

- **평소에는 삭제 버튼을 만들지 않는다.** '편집'을 누른 동안만 ✕ 가 붙고, 그때는
  목적지 버튼이 눌리지 않는다. 아침에 목적지를 탭하다 잘못 누르면 안 된다.
  이 앱의 주 동선은 '아이콘 한 번 탭 → 목적지 한 번 탭'이고 거기에 파괴적인
  버튼을 끼워 넣을 자리가 없다.
- **없는 이름은 404 다.** 조용히 204 를 주면 오타로 지운 줄 알고 넘어간다.
  `repo.delete_place()` 가 rowcount 로 '있었는지'를 돌려주는 이유다.

이름을 경로가 아니라 쿼리로 받는다. 장소 이름에 '/' 가 들어가면(막을 이유가
없다) 경로 파라미터로는 라우팅이 어긋난다.

### (4) 같은 이름 정류장 — 어느 쪽인지 표시

실물 146번에 같은 이름이 길 양쪽에 있는 정류장이 28쌍이다. 둘은 ARS·다음
정류장·행선판이 전부 다르다. 실제 표지판이 '○○ 방면' 을 **다음 정류장**으로
적으므로 그걸 카드에 붙이고, 노선번호 옆에 행선판을 '○○행' 으로 적는다.

- `find_direct_combos()` 가 `board_seq` 를 같이 돌려준다. `MIN()` 하나뿐인
  집계에서 SQLite 가 bare column 을 최소 행에서 가져오는 문서화된 동작을 쓴다.
  같은 정류장을 두 번 지나는 노선에서 엉뚱한 seq 를 집지 않게.
- `repo.board_context()` 가 (노선, seq) → (다음 정류장, 행선지).
- **direction 은 표시용으로만 읽는다.** §2-1 의 조인 사고를 되풀이하지 않도록
  `test_direction_is_never_a_join_condition` 이 강남역9번→1번출구 조합을 지킨다.
- 결과 상단의 구성 요약도 이름이 아니라 **정류장 ID 단위**로 센다. 이름이 겹칠
  때만 '(○○ 방면)' 을 붙인다.

### (5) 검색 → 탭 → 바로 경로. 즐겨찾기는 옵션

홈 맨 위가 검색창이다. 결과를 탭하면 `to_lat/to_lon/to_name` 으로 바로 조회한다.
즐겨찾기를 먼저 만들 필요가 없다. 저장은 결과 화면 헤더의 ☆ 로 한다.

- ☆/★ 판정은 **좌표**로 한다(소수 4자리, 약 11m). 이름은 사용자가 바꿔 저장하므로
  기준이 못 된다. 이미 저장된 곳을 검색으로 가도 ★ 로 뜬다.
- **★ 를 다시 누르면 지운다** (2026-10-05 사용자 요청). 홈 편집 모드의 ✕ 와 같은
  확인 문구를 쓴다(`deleteFavorite()` 공용). 검색으로 간 곳이 다른 이름으로 저장돼
  있으면 그 즐겨찾기 이름으로 묻는다 - 실제로 지워지는 게 그것이기 때문이다.
- 즐겨찾기 이름으로 조회하던 중에 지우면 `lastQuery` 를 좌표로 바꿔 둔다. 안 그러면
  '새로고침' 이 방금 지운 이름을 찾아 404 가 난다.
- '+ 장소 추가' 버튼은 없앴다. '현재 위치를 장소로 저장' 은 검색 화면에 남겼다
  (집을 저장할 때 제일 흔한 경로).
- 홈에 실제 입력칸을 두지 않고 입구 버튼만 둔다. 입력칸이면 포커스가 잡히며
  키보드가 올라와 즐겨찾기 버튼을 가린다.

### (6) 밝은 화면

홈 하단 '화면: 자동 → 밝게 → 어둡게'. 사용자 폰이 다크모드라 늘 어두운 화면이었다.

- `<html data-theme>` 를 **첫 페인트 전에** 인라인 스크립트로 붙인다. CSS 로드 뒤에
  바꾸면 어두운 화면이 한 번 번쩍인다.
- CSS 의 어두운 값은 두 번 적혀 있다 ('자동+기기 다크' 와 '어둡게 고정'). 값을
  바꿀 때 두 곳을 같이 고칠 것.
- **iOS 상태바**: `black-translucent` 는 글자가 늘 흰색이라 밝은 배경에서 시계가
  안 보인다. 밝게일 때는 `default` 로 바꾸게 했다. 이 meta 는 **앱을 켤 때 한 번**
  읽히므로 테마를 바꾸면 다음 실행부터 반영된다. Chromium 에는 iOS 상태바가 없어
  컨테이너에서는 못 봤고, **사용자가 아이폰 홈 화면 앱에서 확인했다** (2026-10-05).

## 1-C. 같은 노선이 여러 장 + 반대 방향 경로 (2026-10-05, 사용자 발견)

사용자 화면: '본사' 로 조회했더니 5536번이 세 장. 30분짜리 옆에 77분·90분짜리가
있었고, 그 둘은 **반대 방향 정류장**에서 타서 반환점을 돌아오는 경로였다.

**원인 (실데이터로 확인).** 5536번은 광명 → 노량진 → 중앙대(seq 34, 반환점) →
노량진 → 광명 을 한 seq 축(1~65)으로 달리는 왕복 노선이다. 반대편 정류장에서 타도
seq 가 증가하므로 직통 조합이 되고, 랭킹이 (정류장, 노선) 단위로 남겨서 같은 노선이
정류장마다 한 장씩 들어갔다.

**고친 것: 노선 하나당 한 장** (`ranking._dedupe`, `planner._rank_sprints`).
같은 노선의 더 나은 경로에 반대 방향 경로가 밀려난다. 사용자의 제안과 같다.

**하지 않은 것: 조합 단계에서 거르기.** 반환점을 지나는 경로는 실제로 도착하고,
§2-1 의 강남역9번→1번출구처럼 짧고 정상인 경우도 있다. direction 으로 거르면 그
사고를 되풀이한다. `test_the_turnaround_ride_is_still_a_valid_combo` 가 지킨다.

**잃는 것:** 같은 노선을 두 정류장에서 탈 수 있을 때 느린 쪽이 안 보인다. 대개 같은
버스를 앞뒤 정류장에서 타는 것이라 대안 가치가 작고, 대안은 다른 노선이 맡는다.
서울 노선 718개는 번호가 겹치지 않아(실측) route_id 로 묶는 게 곧 번호로 묶는 것이다.

**회귀 테스트는 실물 데이터다.** `tests/fixtures/route_5536.json` 은 커밋된 xlsx 에서
5536번 65행을 그대로 뽑은 것이다. 시나리오는 **사용자 위치가 아닌 다른 구간**
(노량진 → 구로디지털단지역)으로 같은 패턴을 재현했다 - §6. 고치기 전 코드에서 핵심
테스트 3개가 실패하는 것을 확인했다.

**교훈은 §2 와 같다.** 146번 픽스처(단방향처럼 보이는 노선 하나)로는 안 보이는
버그였다. 개발 컨테이너에서도 `data/raw/*.xlsx` 로 실데이터 DB 를 3초 만에 만들 수
있다 (`nowbus db build <xlsx> --db <스크래치 경로>`). 경로가 이상하다는 제보가 오면
그 노선부터 실데이터로 뽑아 볼 것.

## 1-D. 혼잡도 글자 표시 (2026-10-05, v4)

카드의 `혼잡도 3` 을 `혼잡도 여유` 로 바꿨다 (3 여유 / 4 보통 / 5 혼잡 / 6 매우 혼잡,
그 외 숫자 그대로). **변환은 `app.js` 에만 있다** - 사용자가 '숫자 자리에 글자만
바꾸면 된다' 고 해서 서버·API 계약은 건드리지 않았다. CLI 는 여전히 숫자다.

코드 의미의 근거: 서울시 발표와 API 안내를 인용한 검색 결과 두 건이 3·4·5 에 대해
일치. 공식 원문(data.go.kr)은 컨테이너에서 막혀 직접 대조 못 했다. 6 은 자료가
엇갈린다. 산정 기준은 교통카드 승하차로 추정한 차내 인원 + 차량 크기.

## 1-E. 공통: 폰에 옛 화면이 남는 문제와 화면 검증 방법

### 폰에 옛 화면이 남는 문제 (실제로 겪었다)

서버는 새 `app.js` 를 주는데("`curl .../app.js | grep -c sprint`" 로 확인됨)
브라우저가 계속 옛 것을 실행해서 '장소 추가'가 좌표 입력 prompt 로 나왔다.
service worker 가 network-first 라 괜찮을 거라고 봤지만 아니었다.

세 가지를 넣었다.

1. `index.html` 이 `/app.js?v=4.3`, `/style.css?v=4.3` 를 참조한다(2026-10-05 기준). **URL 이
   달라지면 캐시가 옛 파일을 내줄 방법이 없다.** `app.js`/`style.css` 를 고치면
   **항상** 이 값과 `sw.js` 의 `VERSION` 을 바꾼다.

   **홈 화면의 `v4` 표시(사용자가 보는 버전)와 캐시 키는 별개다.** 사용자가 문구
   수정을 v5 로 올리지 말고 v4 에 포함하자고 했다. 그렇다고 캐시 키까지 `?v=4` 로
   되돌리면 폰에 캐시된 옛 v4 파일이 계속 쓰인다. 그래서 같은 버전 안에서 고칠 때는
   표시는 그대로 두고 캐시 키만 `4.1`, `4.2` 처럼 올린다. 새 기능 묶음을 내면 표시를
   올린다(v5).
2. `sw.js` 의 SHELL 에서 버전 붙은 자산을 뺐다. URL 을 박아두면 `?v=` 를 올릴
   때마다 같이 고쳐야 하고, 안 고치면 옛 URL 을 캐시한다.
3. 새 워커가 넘겨받으면(`controllerchange`) 한 번만 새로고침한다. 홈 화면에
   추가한 PWA 는 탭을 닫는 일이 없어서 이게 없으면 옛 화면이 며칠 살아 있는다.

홈 화면 제목 옆 작은 **`v4`** 가 지금 어느 버전을 보고 있는지 알려준다.
사용자가 "화면이 똑같다"고 할 때 이걸 먼저 물어볼 것.

옛 캐시가 박힌 상태를 Chromium 으로 재현해서(`nowbus-v1` 캐시에 옛 app.js 를
넣고) 새 코드가 뜨는 것까지 확인했다.

### 검증 방법

목 Provider + Chromium 으로 세 화면을 확인했다. 스크린샷 경로는 세션 스크래치라
남지 않지만, 재현 방법은 이렇다 (`playwright` 는 pip 로 따로 깔아야 한다):

- `webapp.build_provider` 를 목으로 갈아끼운 뒤 `create_app()` 을 부른다.
  **`app.state.provider` 에 직접 넣으면 lifespan 이 덮어쓴다** - 테스트가
  lifespan 을 안 타서 지금까지 문제가 없었을 뿐이다.
- Chromium 실행 경로는 `/opt/pw-browsers/chromium-1194/chrome-linux/chrome`.
- localhost 로 curl 할 때는 `NO_PROXY=127.0.0.1` 을 붙인다. 안 붙이면 에이전트
  프록시를 타면서 "Invalid HTTP request" 가 난다.

## 2. 사용자가 잡아준 것 — 같은 실수 반복하지 말 것

이 대화에서 **내가 틀린 것을 사용자가 세 번 잡았다.** 전부 "그럴듯한 추론"이나
픽스처 한 노선만 본 결과가 실제 데이터와 달랐던 경우다. 새 세션도 같은 함정에
빠지기 쉽다.

### 2-1. `direction` 조인 (내가 넣었다가 되돌림)

`route_stop.direction` 이 행선지 종점명이라는 걸 알고, "회차 지점을 넘는
조합은 종점까지 갔다 와야 한다"고 **잘못 추론해** §9.1 질의에 조인을 걸었다.

사용자 지적: *"강남역9번출구에서 타면 진흥아파트, 서초푸르지오써밋,
신논현역 지나서 강남역1번출구 도착하는데, seq 66에서 70이면 4정거장 뒤인데
왜 상계동 종점에 가야 한다는 거지?"*

맞는 지적이었다. 데이터를 다시 보니 회차점은 종점이 아니라 **노선 한복판**
(기점에서 가장 먼 seq 67, 18.4km)이고 seq 135는 기점으로 돌아온다. 차량은
seq 1→N 을 연속으로 달리고 `direction` 은 앞 행선판이 바뀌는 것뿐이다.

→ 조인 제거. 조건은 `rs2.seq > rs1.seq` 하나.
→ `test_turnaround_point_is_mid_route_not_the_terminal` 이 전제를 고정한다.
**이 테스트를 지우거나 direction 조인을 되살리지 말 것.**

### 2-2. 후보 상한을 조합 탐색 *전에* 적용

`MAX_ORIGIN_STOPS=8` 을 거리순으로 먼저 잘랐다. 실데이터에서 드러났다:
강남역 반경 600m 정류장 39곳 중 시청행 직통이 있는 곳은 8곳뿐인데 거리순
상위 8곳과 거의 겹치지 않는다. 먼저 자르면 노선 9개 중 1개만 남았다.

→ 조합을 먼저 찾고 '직통이 있는 승차 정류장' 중에서 자른다.
→ 하차 쪽 상한(`max_dest_stops`)은 외부 호출이 없어 제거했다.
**config 에 다시 추가하지 말 것.**

### 2-3. 같은 노선이 정류장마다 한 장씩 (2026-10-05)

랭킹이 (정류장, 노선) 단위로 남겨서, 왕복 노선(5536번)이 반대편 정류장에서 타
반환점을 돌아오는 77·90분짜리 경로까지 카드로 냈다. 사용자가 화면을 보고 "반대로
가는 경로다" 라고 잡았다. 자세한 건 §1-C.

→ 노선 하나당 한 장. **조합 단계(direction)로 거르지 않았다** - 2-1 의 재발이 된다.

### 교훈

픽스처 한 노선(146번)으로는 못 잡는 종류의 버그였다. **실데이터로 한 번
돌려보는 것**이 테스트보다 먼저 잡아낸다.

## 4. 환경 — 이걸 모르면 헤맨다

### 개발 컨테이너 (Claude Code 가 도는 곳)

**외부 API 가 조직 이그레스 정책에 막혀 있다.**
`ws.bus.go.kr`, `apis.data.go.kr`, `data.go.kr`, `data.seoul.go.kr` 전부 403.
**`dapi.kakao.com`(카카오 로컬)도 마찬가지로 CONNECT 거부된다** — 장소 검색을
붙이면서 확인했다. `nominatim.openstreetmap.org` 도 막혀 있다.

- `scripts/smoke.py`, `scripts/smoke_geocode.py`, `nowbus plan` 은 **여기서 실행
  불가**. 로컬에서만 된다.
- 테스트 163개는 전부 오프라인(픽스처 기반)이라 여기서 돈다.
- 프론트 확인은 목 Provider + Chromium 으로 했다.
  Playwright 는 pip 버전이 달라 `executable_path="/opt/pw-browsers/chromium-1194/chrome-linux/chrome"`
  를 줘야 한다. `playwright install` 은 실행하지 말 것.
- **컨테이너는 새로 뜰 때마다 비어 있다.** 시작하면 먼저:
  `python -m venv .venv && .venv/bin/pip install -e ".[dev]"` (화면 확인이 필요하면
  `.venv/bin/pip install playwright` 추가). 시스템의 ruff/pytest 는 의존성이 없어서
  `.venv/bin/pytest` 로 돌려야 한다.
- **실데이터 DB 는 여기서도 만들 수 있다.** `data/raw/*.xlsx` 가 커밋돼 있어서
  `.venv/bin/python -m nowbus.cli db build "$(ls data/raw/*.xlsx)" --db <스크래치>/real.db`
  가 3초면 끝난다. 경로가 이상하다는 제보는 이걸로 먼저 확인할 것 (§1-C).
- 웹 검색(WebSearch)은 되지만 data.go.kr · news.seoul.go.kr · api.bus.go.kr 원문은
  WebFetch 로도 막혀 있다. 공식 명세를 인용할 때는 확인 수준을 같이 말할 것.

### 사용자 로컬

**집 = macOS (zsh). 서버도 맥이다.** 세션 초반엔 Windows(cmd)였다가 맥으로 옮겼다.

**밖에서는 Windows(PowerShell)를 쓸 때가 있다.** 그때는 PowerShell 명령을 준다
(`Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass` 후
`.venv\Scripts\Activate.ps1`, 한글 파일명은 `(Get-ChildItem data\raw\*.xlsx).FullName`).
API 키는 맥의 `.env` 에만 있다 - 윈도우에서 돌리려면 data.go.kr · 카카오 개발자
콘솔에서 키를 다시 **확인**(재발급 아님)하면 된다. `NOWBUS_API_TOKEN` 은 아무 값이나.

**zsh 에 줄 명령에는 `#` 주석을 붙이지 말 것.** zsh 대화형 셸은 `#` 를 주석으로
안 봐서 뒤 글자가 인자로 들어간다(`grep: #: No such file` 을 실제로 냈다).

배포는 **D-9 = A안(집 PC + 터널)** 으로 확정. 다만 Cloudflare Tunnel 이
아니라 **Tailscale Funnel** 을 쓴다:

- `trycloudflare.com` URL 은 재시작마다 바뀌어서 홈 화면 아이콘이 죽는다.
  "아침에 아이콘 한 번 탭"이라는 MVP 완료 정의와 맞지 않는다.
- Tailscale Funnel 은 도메인 없이 `https://<맥>.<tailnet>.ts.net` 고정 주소를
  무료로 준다. `brew install --cask tailscale-app` (CLI 전용
  `brew install tailscale` 은 데몬이 root 를 요구해서 막힌다).

### 매일 아침 돌아가야 하는 것

```zsh
tailscale funnel --bg 8000     # 한 번만. 재부팅해도 유지
caffeinate -is nowbus serve    # 이건 계속 떠 있어야 함
```

- 화면 잠김·디스플레이 꺼짐은 괜찮다. **시스템 잠자기**가 서버를 죽인다.
- `-s` 는 **충전기가 꽂혀 있을 때만** 잠자기를 막는다. `-i` 는 배터리에서도
  유휴 잠자기를 막는다. 그래서 둘 다 준다. 다만 배터리로 밤을 새우면 방전 직전에
  macOS 가 결국 잠든다 - `-i` 는 보험이지 해결책이 아니다.
- **뚜껑 닫기는 어느 쪽도 못 막는다.**
- launchd 자동 실행은 만들자고 제안했으나 사용자가 "일단 써보고" 로 보류.

**실측 (2026-09-30 아침): 충전기 없이 `caffeinate -s` 로 밤을 넘겼더니 아침에
서버가 죽어 있었다.** 폰에서는 화면이 서비스 워커 캐시로 멀쩡히 뜨고 데이터만
'Load failed' 로 비어 보여서 원인을 알기 어려웠다(안내 문구로 고침. v4 에 포함).
D-9(집 PC + 터널) 의 전제는 '맥이 밤새 충전기에 꽂혀 뚜껑 열린 채 있다' 이다.
이게 일상적으로 지켜지지 않으면 B안(클라우드 상주)을 다시 검토해야 한다.

### ⚠️ 먼저 확인할 것: 같은 정류장을 두 번 지나는 노선의 도착정보 (미확인 위험)

2026-10-05, 사용자가 '5616번이 재밌다' 고 해서 실데이터로 뽑아 보다가 발견했다.
**아직 고치지 않았다. 실물 응답으로 확인한 다음에 고칠 것** (§3 원칙).

**확인된 사실** (실데이터 DB 와 픽스처로 확인)

- 5616번(`100100273`, 116정거장)은 가산 → 난곡 왕복 → 구로디지털단지 → 영등포 →
  목동 → 영등포 → 구로디지털단지 → **난곡 왕복 한 번 더** → 가산 이다. 같은 정류장
  ID 를 두 번 지나는 곳이 **19개**. 예: 난곡우체국사거리 `120000116` 이 seq 14 와 87
- 서울 노선 718개 중 **224개**가 같은 정류장 ID 를 두 번 이상 지난다. 드문 경우가 아니다
- `find_direct_combos()` 는 같은 (노선, 승차, 하차)면 **가장 짧은 경우만** 남긴다.
  난곡우체국사거리 → 구로디지털단지역(`116000138`, seq 107)은 seq 87 에서 타면 20정거장,
  seq 14 에서 타면 93정거장(목동을 다 돈다)인데 20 으로 잡힌다
- 도착정보 응답(`getStationByUid`)의 `itemList` 마다 **`<staOrd>`(그 노선에서의 정류장
  순번)가 온다** (`tests/fixtures/getStationByUid.xml` 에 있음. 예: 340번 staOrd 56).
  **`parse_arrivals()` 는 이 값을 읽지 않는다.** 플래너도 도착정보를 노선 ID 로만
  짝짓는다 (`planner.py` 의 `on_route = [... if a.route_id == c.route_id]`)

**위험** - 정류장에 오는 버스가 '첫 번째로 지나는 중' 인데 NowBus 는 '두 번째로 지나는
중'(짧은 쪽) 으로 계산할 수 있다. 그러면 카드는 "20정거장, 9분 후" 인데 실제로는 그
버스가 목동을 다 돌고 온다. 에러 없이 '가끔 이상한 추천' 으로만 나타난다 - §3 의
stId 버그와 같은 종류다.

**모르는 것** - 이런 정류장에서 API 가 **같은 노선을 staOrd 별로 두 건** 주는지, 한
건만 주는지(그럼 어느 쪽인지). 개발 컨테이너에서는 API 가 막혀 확인할 수 없었다.

**확인 방법** (사용자 맥에서) - 5616번이 두 번 지나는 정류장, 예를 들어
난곡우체국사거리(ARS 는 실데이터 DB 에서 `stop_id=120000116` 으로 찾는다)를
`getStationByUid` 로 조회해 원본을 `tests/fixtures/` 에 저장한다. `scripts/smoke.py`
를 고쳐 쓰거나 같은 방식으로 받는다. 5616번 `itemList` 가 몇 건이고 각각 staOrd 가
무엇인지 본다.

**고치는 방향 (확인 후)** - `Arrival` 에 `sta_ord` 를 넣고, 플래너에서 도착정보를
조합의 `board_seq` 와 맞춰 짝짓는다. 두 건이 오면 각 pass 를 따로 계산하고, 한 건만
오면 staOrd 가 가리키는 pass 의 승차 구간으로 계산한다. 그 pass 에서 목적지에 가지
않으면 그 차는 후보에서 뺀다. 회귀 테스트는 5616번 실데이터 픽스처 + 받아 둔 실물
응답으로 만든다 (§1-C 의 5536번과 같은 방식).

### 사용자 응답 대기 중

**아직 답을 못 받은 것**:

- 도보 예상 vs 실제 (→ `WALK_DETOUR` 1.30, `CALIB`)

  못 탔다면 어디서 잃었는지 - 신호등이면 속도를 낮추는 게 아니라 고정 페널티를
  넣어야 한다.
- **장소 검색으로 찾으려던 곳이 안 나온 사례**

  버스인지 반경 문제인지 실데이터 DB 로 확인할 것

## 8. 작업 스타일

사용자 선호(설정에 등록돼 있음):

- **한국어**, 주로 Python
- **설명은 핵심만 확실히.** 장황한 나열보다 결론과 근거
- **모르는 건 모른다고.** 웹 검색으로도 확인 안 되면 추측하지 말고 그렇게 말할 것

이 대화에서 실제로 잘 작동한 방식:

- 데이터 모양이 의심되면 **추측하지 말고 실물을 받아서 확인**한다
- 사용자가 반론하면 **먼저 데이터를 다시 본다.** 세 번 다 사용자가 옳았다
- 작업 단위마다 커밋하고, 커밋 메시지에 **왜 그렇게 했는지**를 남긴다
  (특히 계획서와 다르게 간 경우)
- 사용자가 로컬에서 할 일과 컨테이너에서 할 일을 명확히 나눠서 안내한다

이 대화에서 사용자에게 지적받은 것 (반복하지 말 것):

- **README·설계서·인계 메모를 기능과 같이 고칠 것.** README 누락을 두 번 지적받았다
  ("또 readme 갱신 안했다 그치?!"). 기능 커밋을 낼 때 세 문서에 해당 줄이 있는지
  확인한다
- **사용자가 범위를 구체적으로 말하면 그 범위대로.** 혼잡도 표시를 서버 변환 + API
  필드 + 테스트로 키웠다가 두 번 멈췄다 - 사용자는 화면의 숫자를 글자로 바꾸는 한
  줄을 원했다. 구조를 키울 이유가 있으면 만들기 전에 묻는다
- **명령 예시의 자리표시자를 진짜 값처럼 쓰지 말 것.** `echo 'KEY=발급받은키'` 를
  그대로 실행해 `.env` 에 한글이 들어갔다. `<여기에 키>` 처럼 쓰거나 편집기로
  열게 안내한다
