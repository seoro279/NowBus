# 프로그램 설계서 — "지금 나가면?" 버스 탑승 추천기

> 코드명: **NowBus** (가칭)
> 문서 버전: **v0.2** (D-2 결과물 형태 → 모바일 웹, D-8 출력 5개 반영)
> 작성일: 2026-08-26

---

## 1. 한 줄 정의

> **현재 위치에서 지금 출발했을 때, 실제로 걸어서 닿을 수 있는 정류장·버스 조합만 추려서 목적지 도착이 가장 빠른 순으로 알려주는 프로그램.**

---

## 2. 배경 — 왜 만드는가

### 2.1 네이버 지도의 구조적 한계

| 문제 | 설명 |
|---|---|
| **탑승 가능성 미검증** | 도보 6분 거리 정류장에 3분 뒤 오는 버스를 "3분 후 도착"이라고 그대로 표시. 실제로는 못 타는 버스. |
| **경로 우선, 정류장 후순위** | 경로를 먼저 확정하고 도착정보를 붙이는 순서라, "다른 정류장으로 갔으면 더 빨랐을" 선택지가 아예 후보에서 빠짐. |
| **불필요한 환승 추천** | 무환승 최단 노선이 아래로 밀리고 환승 경로가 상단에 노출되는 사례가 반복 보고됨. |
| **정류장 매칭 부정확** | 출발 좌표가 조금만 달라져도 인근 정류장을 놓치고 먼 전철역으로 안내. |
| **역산 부재** | "몇 시에 나가야 하나"를 사용자가 매번 암산해야 함. |

### 2.2 우리가 뒤집는 순서

```
네이버:  목적지 입력 → 경로 탐색 → 경로별 도착정보 표시 → 사용자가 판단
NowBus:  현재 위치 + 목적지 → 도달 가능 정류장 전개 → 직통 노선 조합 전개
         → 실시간 도착으로 탑승 가능성 필터 → 총 도착시각 순 정렬
```

핵심은 **catchability(탑승 가능성)** 를 1급 개념으로 올리는 것. 이게 이 프로그램의 존재 이유이자 유일한 차별점.

## 3. 사용 시나리오

### UC-1. 아침 출근 (주 사용 케이스)
> 집에서 나가기 직전. "지금 나가면 회사까지 어떻게 가는 게 제일 빠르지?"

- 입력: (즐겨찾기) 집 → 회사, 지금
- 조작: 폰에서 홈 화면 아이콘 탭 → "회사" 버튼 1탭 (GPS는 그 사이 자동 획득)
- 출력: 상위 5개 카드 (정류장, 노선, 여유시간, 예상 도착시각)

### UC-2. 외출 중 귀가
> 낯선 곳에서 집으로. 어느 정류장으로 걸어가야 할지 모름.

- 입력: 현재 좌표(수동 입력 또는 GPS) → 집
- 출력: 동일. 정류장까지의 도보 경로 안내 링크 포함

### UC-3. 역산 (v2)
> "9시 30분까지 도착해야 하는데 몇 시에 나가야 해?"

- 목표 도착시각 역산 → 마지노선 출발시각 알림

## 4. 범위

### 4.1 MVP 포함 (In Scope)

- **무환승 직통 버스만** 탐색
- 출발지/목적지 **양쪽 모두 인근 정류장 후보를 복수로 전개**
- 실시간 도착정보 기반 탑승 가능성 판정
- 총 소요시간 기준 랭킹 + **상위 5개** 출력
- 즐겨찾기 장소 등록 (집/회사 등)
- **모바일 웹 UI** — iOS Safari에서 링크로 접속, 홈 화면 추가 시 앱처럼 동작 (PWA)
- **GPS 기반 현재 위치 자동 획득** (브라우저 Geolocation API)

### 4.2 MVP 제외 (Out of Scope)

| 제외 항목 | 사유 |
|---|---|
| 환승 경로 | 조합 폭발. 무환승만으로도 UC-1/2의 대부분을 커버. v2에서 1회 환승까지 확장 |
| 지하철 | 시간표 기반이라 로직이 완전히 다름. 별도 모듈로 v2 |
| 임의 목적지 지오코딩 | 즐겨찾기 + 좌표 직접 입력으로 시작 |
| **iOS 네이티브 앱 (Swift)** | PWA로 체감 대부분을 확보 가능. 별도 언어 스택 + 개발자 계정 비용 + 심사 부담이 MVP 대비 과함. §14에서 v3 재검토 |
| 지속적 GPS 추적 | 요청 시점 좌표 1회만 사용 (배터리·권한 부담) |
| 지도 렌더링 | 카드형 텍스트 UI가 이동 중 판독에 더 빠름 (네이버의 "정보 과밀" 문제 반면교사). 정류장 위치는 지도앱 딥링크로 위임 |
| 로그인 / 다중 사용자 | 개인 사용 전제. 접근 통제는 비공개 URL + 토큰으로 |

## 6. 핵심 알고리즘

### 6.1 전체 흐름

```
입력: 현재좌표 P_now, 목적지좌표 P_dst, 현재시각 t_0

1) S_org = 반경 R_org(기본 600m) 내 정류장 집합        [F-01]
   S_dst = 반경 R_dst(기본 700m) 내 정류장 집합

2) 각 s ∈ S_org 에 대해 t_walk(s) 계산                  [F-02]
   각 d ∈ S_dst 에 대해 t_walk_dst(d) 계산

3) 유효 직통 조합 C 전개 (SQLite 질의)                   [F-03]
   C = { (s, r, d) | 노선 r이 s → d 순서로 경유 }

4) S_org 에 대해 실시간 도착정보 병렬 조회               [F-04]
   → t_arr(s, r, k), k = 1차/2차 도착 차량

5) 각 (s, r, d) 에 대해 탑승 가능성 판정                 [F-05]
   → 탈 수 있는 최초 차량 k* 선택

6) 총 소요시간 계산                                     [F-06]

7) 점수화 → 정렬 → 상위 N 출력                          [F-07]
```

### 6.2 탑승 가능성 판정 (핵심)

```
margin(s, r, k) = t_arr(s, r, k) - t_walk(s)
```

| margin | 등급 | 처리 |
|---|---|---|
| ≥ M_safe (기본 2분) | **SAFE** | 정상 후보 |
| 0 ≤ margin < M_safe | **TIGHT** | 후보 유지, "뛰어야 함" 경고 + 점수 페널티 |
| < 0 | **MISS** | 해당 차량 탈락 → 다음 차량(k+1)으로 재판정 |

- 1차·2차 차량 모두 MISS면 **배차간격(headway)** 으로 3차 도착을 추정하여 참고용 후보로만 유지
- `M_safe`는 설정값. 여유 있게 다니고 싶으면 3~4분으로 올림

### 6.3 총 소요시간

```
T_total = max( t_arr(s,r,k*), t_walk(s) )   # 정류장 도착 or 버스 도착 중 늦은 쪽
        + t_ride(s → d, r)                  # 승차 구간
        + t_walk_dst(d)                     # 하차 후 도보
```

> `max(...)` 형태인 이유: 탈 수 있는 버스라면 "도보시간 + 대기시간"은 결국 버스 도착시각과 같음. 반대로 도보가 더 오래 걸리면 도보시간이 지배.

### 6.4 점수화

```
score = T_total
      + w_tight   × 1[등급 = TIGHT]          # 기본 3.0 (분 환산 페널티)
      + w_walk    × (t_walk + t_walk_dst)    # 기본 0.2, 도보 기피 성향
      + w_transfer× n_transfer               # MVP는 항상 0
```

`score` 오름차순 정렬. 가중치는 설정 파일로 노출해 사용자가 조정 가능.

### 6.4.1 다양성 보정 (상위 5개 출력에 따른 추가 규칙)

> 출력을 3개에서 **5개로 늘리면서 새로 생긴 문제**: 정렬만 하면 5개가 전부 같은 정류장의 노선으로 채워질 수 있다. 그러면 "그 정류장까지 못 가는 상황"에 대한 대안이 화면에 하나도 없어서, 후보를 늘린 의미가 사라진다.

정렬 후 다음 규칙으로 선별:

```
1. score 오름차순 정렬
2. 동일 board_stop 은 최대 2개까지만 채택
3. 그렇게 5개가 안 차면, 제한을 풀고 나머지를 score 순으로 채움
4. 최소 2개 이상의 서로 다른 정류장이 결과에 포함되도록 보장
```

- 동일 `(board_stop, route)` 중복은 항상 제거 (같은 노선의 2차 차량은 1차가 MISS일 때만 등장)
- 결과 카드에는 정류장별로 시각적 구분을 줘서, "A정류장 2개 / B정류장 2개 / C정류장 1개" 구조가 한눈에 보이게 함

### 6.5 도보 시간 추정

```
d_haversine = 두 좌표 간 대권거리(m)
d_effective = d_haversine × DETOUR (기본 1.30, 도로 우회 보정)
t_walk      = d_effective / SPEED × CALIB
```

- `SPEED` 기본 67 m/min (약 4km/h)
- `CALIB` 개인 보정계수, 초기 1.0 → F-11 피드백으로 갱신
- v2에서 카카오/네이버 도보 경로 API로 교체 가능하도록 인터페이스 분리

## 7. 데이터 소스

### 7.1 정적 데이터 (1회 수집 후 주기 갱신)

| 데이터 | 출처 | 비고 |
|---|---|---|
| 정류장 목록 + 좌표 | 서울 열린데이터광장 / 공공데이터포털 TAGO | ARS ID 포함 |
| 노선 목록 | 동일 | |
| **노선별 경유 정류장 순서** | 동일 (`getStaionByRoute` 계열) | **가장 중요.** 이게 있어야 직통 조합 탐색 가능 |

> 노선 수백 개 × 정류장 수십 개 규모. 수집 1회에 수 분~수십 분 소요 예상. 주 1회 갱신 배치.

### 7.2 실시간 데이터 (요청 시 조회)

| 데이터 | 출처 | 제공 필드 |
|---|---|---|
| 정류장별 도착 예정 | 서울시 버스도착정보 API | 1·2차 도착 예정시간, 차량번호, **혼잡도**, 만차 여부, 막차 여부, **배차간격**, 예정여행시간 |

### 7.3 대안/보조

- **ODsay LAB API**: 전국 커버, 반경 내 정류장 조회 + 대중교통 길찾기. 서울 외 지역 확장 시 주력. 무료 티어 호출 한도 확인 필요.
- **TAGO 국가대중교통정보**: 전국 버스 도착/노선/정류장.

> ⚠️ 지역별로 API가 갈리므로, **Provider 인터페이스로 추상화**하여 지역별 구현체를 갈아끼울 수 있게 설계한다.

## 8. 시스템 아키텍처

> **D-2 변경(모바일 웹)에 따라 단일 프로세스 → 서버·클라이언트 2계층 구조로 전환됨.**

```
📱  iOS Safari / 홈 화면 PWA
    ├─ Geolocation API로 현재 좌표 획득          [F-16]
    ├─ 결과 카드 5장 렌더링                       [F-15]
    └─ manifest + service worker (앱 셸 캐시)     [F-17]
                    │
                    │  HTTPS   GET /api/plan?lat=&lon=&to=회사
                    ▼
┌─────────────────────────────────────────────────┐
│  FastAPI 서버                                    │
│    ├─ routes/api.py     JSON 응답        [F-14]  │
│    ├─ routes/static     PWA 정적 파일 서빙       │
│    └─ (debug) CLI       개발·검증용 진입점       │
└───────────────────┬─────────────────────────────┘
                    │
┌───────────────────▼─────────────────────────────┐
│  Planner  (오케스트레이션) — 인터페이스 무관 순수 로직 │
│    ├─ candidates.py   직통 조합 전개             │
│    ├─ walking.py      도보 시간 추정             │
│    ├─ catchability.py 탑승 가능성 판정           │
│    └─ ranking.py      점수화 / 정렬 / 다양성 보정 │
└───────┬──────────────────────────┬──────────────┘
        │                          │
┌───────▼──────────┐    ┌──────────▼──────────────┐
│  Static Repo     │    │  Arrival Provider (ABC) │
│  (SQLite)        │    │   ├─ SeoulProvider      │
│  stop/route/     │    │   └─ OdsayProvider      │
│  route_stop      │    │        + TTL Cache      │
└───────▲──────────┘    └─────────────────────────┘
        │
┌───────┴──────────┐
│  Collector 배치   │  ← 주 1회 실행
└──────────────────┘
```

**설계 원칙**
1. 실시간 조회와 정적 조회를 분리 — 정적 데이터는 절대 요청 경로에서 API를 부르지 않는다.
2. Provider는 추상 인터페이스 — 지역 확장 시 Planner를 건드리지 않는다.
3. **Planner는 인터페이스에 무지하다** — FastAPI든 CLI든 봇이든 `plan_now()` 하나만 호출. D-2가 또 바뀌어도 코어는 그대로.
4. **API 키는 서버에만 존재** — 클라이언트가 공공 API를 직접 부르지 않는다. 키 노출 방지 + CORS 문제 회피.
5. CLI는 폐기하지 않고 **개발·디버깅 도구로 유지** — 원칙 3 덕분에 유지 비용이 거의 0.

### 8.1 배포 구조

MVP 기준 두 가지 선택지. 어느 쪽이든 **HTTPS가 필수**다 (iOS Safari는 HTTP에서 Geolocation을 차단한다).

| 방식 | 구성 | 장점 | 단점 |
|---|---|---|---|
| **A. 집 PC + 터널** | uvicorn 로컬 실행 + Cloudflare Tunnel | 무료, HTTPS 자동, DB 그대로, 설정 5분 | PC가 꺼져 있으면 접속 불가 |
| **B. 클라우드 상주** | Fly.io / Railway / Oracle Cloud 무료 티어 | 24시간 가용 | DB 파일 배포·갱신 절차 필요 |

> **권장: A로 시작 → 실사용이 정착되면 B로 이전.** 아침 출근 시간에 집 PC가 켜져 있는지가 관건이므로, Phase 5 실사용 검증에서 판단한다.

### 8.2 API 엔드포인트

```
GET  /api/plan?lat={lat}&lon={lon}&to={place_name}     → 후보 5개 JSON
GET  /api/plan?from={place_name}&to={place_name}       → 즐겨찾기 기반 (GPS 실패 폴백)
GET  /api/places                                       → 즐겨찾기 목록
POST /api/places                                       → 즐겨찾기 등록
POST /api/feedback                                     → 실측 도보시간 기록  [F-11]
GET  /                                                 → PWA 셸 (HTML)
```

- 인증: 쿼리스트링 또는 헤더의 **고정 토큰 1개**. 개인용이므로 이 정도면 충분.
- 응답에 `generated_at`을 포함해 클라이언트가 "N초 전 정보"를 표시할 수 있게 함.

## 9. 데이터 모델 (SQLite)

```sql
CREATE TABLE stop (
    stop_id     TEXT PRIMARY KEY,   -- 내부 정류장 ID
    ars_id      TEXT,               -- 정류장 고유번호(사용자 표시용)
    name        TEXT NOT NULL,
    lat         REAL NOT NULL,
    lon         REAL NOT NULL,
    city_code   TEXT
);
CREATE INDEX idx_stop_geo ON stop(lat, lon);

CREATE TABLE route (
    route_id    TEXT PRIMARY KEY,
    route_name  TEXT NOT NULL,      -- "146", "360"
    route_type  TEXT,               -- 간선/지선/광역 등
    headway_min REAL,               -- 평시 배차간격(참고용)
    city_code   TEXT
);

CREATE TABLE route_stop (           -- ★ 핵심 테이블
    route_id    TEXT NOT NULL,
    stop_id     TEXT NOT NULL,
    seq         INTEGER NOT NULL,   -- 경유 순서
    direction   INTEGER,            -- 상행/하행
    PRIMARY KEY (route_id, seq),
    FOREIGN KEY (route_id) REFERENCES route(route_id),
    FOREIGN KEY (stop_id)  REFERENCES stop(stop_id)
);
CREATE INDEX idx_rs_stop ON route_stop(stop_id);

CREATE TABLE place (                -- 즐겨찾기
    name        TEXT PRIMARY KEY,   -- "집", "회사"
    lat         REAL NOT NULL,
    lon         REAL NOT NULL
);

CREATE TABLE trip_log (             -- 실측 피드백
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    created_at  TEXT,
    stop_id     TEXT,
    predicted_walk_min REAL,
    actual_walk_min    REAL
);
```

### 9.1 직통 조합 탐색 질의 (F-03의 실체)

```sql
SELECT rs1.route_id,
       rs1.stop_id AS board_stop,
       rs2.stop_id AS alight_stop,
       rs2.seq - rs1.seq AS n_stops
FROM route_stop rs1
JOIN route_stop rs2
  ON rs1.route_id  = rs2.route_id
 AND rs1.direction = rs2.direction
WHERE rs1.stop_id IN (:origin_stop_ids)
  AND rs2.stop_id IN (:dest_stop_ids)
  AND rs2.seq > rs1.seq;                -- 방향성 보장
```

이 한 방 질의로 "탈 수 있는 모든 직통 조합"이 나온다. 프로그램의 심장.

### 10.2 인터랙션 원칙

| 원칙 | 내용 |
|---|---|
| **1탭 도달** | 앱 열기 → 목적지 버튼 1탭 → 결과. 그 이상 없음 |
| **선(先)위치 획득** | 화면 진입 즉시 GPS를 요청해, 사용자가 목적지를 고르는 사이 좌표 확보 완료 |
| **큰 터치 타겟** | 버튼 최소 높이 56px. 걸으면서 누른다는 전제 |
| **판독 우선순위** | 정류장 이름 > 여유시간 등급 > 노선번호 > 도착시각 순으로 시각 위계 |
| **신선도 표시** | "3초 전" 같은 갱신 경과 표시. 30초 지나면 흐리게 처리 |
| **정류장 탭** | 지도앱 딥링크로 도보 안내 위임 [F-18] |

### 10.3 상태별 처리

| 상태 | 화면 |
|---|---|
| GPS 권한 거부 | "현재 위치를 쓸 수 없어요" + 즐겨찾기 출발지 선택 UI로 폴백 |
| 결과 0건 | "지금 걸어서 탈 수 있는 직통 버스가 없어요" + 반경 확대 버튼 |
| 전부 MISS | 결과는 보여주되 상단에 "지금 나가면 다 놓쳐요. N분 뒤 출발 권장" 배너 |
| 막차 이후 | 해당 노선 카드에 막차 종료 표시 |
| API 지연 | 스켈레톤 카드 표시. 3초 초과 시 부분 결과라도 노출 |

- ✅ / ⚠️ / ❌ 로 catchability를 한눈에. **색상에만 의존하지 않는다** (햇빛 아래 판독성)
- 정보 밀도를 낮게 유지 — 네이버의 "정보 과밀" 문제 반면교사

## 14. 향후 확장 (v2 이후)

1. **1회 환승 경로** — `route_stop` 자기조인 2단계 + 환승 정류장 후보 제한
2. **출발 역산 알림** (F-13) — 목표 도착시각에서 거꾸로 계산해 PWA 웹 푸시로 통지. iOS는 홈 화면 추가된 PWA에서만 푸시가 동작하므로 F-17이 선행 조건
3. **정시성 통계** — 도착정보를 장기 수집해 노선별 배차 분산 산출 → 도착시각을 구간으로 제시 ("18~26분")
4. **개인화 학습** — 실제 선택 이력으로 가중치(`w_tight`, `w_walk`) 자동 튜닝
5. **날씨 연동** — 비 오는 날 `w_walk` 자동 상향
6. **iOS 네이티브 앱 (v3)** — PWA로 부족함이 확인될 경우에만. 위젯·백그라운드 위치·안정적 푸시가 필요해지는 시점이 기준. 서버 API는 그대로 재사용 가능하므로 전환 비용은 클라이언트에 국한됨
